## Failure #1: Analysis Header Not Found

**Test**: `analysis.spec.ts:113` - "should display analysis metadata"  
**Error**: `getByTestId('analysis-header')` not found, even after waiting for completion

### Root Cause Identified

**The Problem:**
The `AnalysisHeader` component **IS** included in both `CompletedAnalysisView` and `CommonAnalysisLayout`, and the test ID **IS** correctly added. However, the header is **not rendering** for completed analyses in the test environment.

**Why This Happens:**

1. **Metadata Dependency**: `AnalysisHeader` receives `analysisMetadata` as a prop:
   ```tsx
   <AnalysisHeader
     title={analysisMetadata?.title || 'Content Analysis'}
     url={analysisMetadata?.url || (analysisId ? `Analysis ID: ${analysisId}` : '')}
     ...
   />
   ```

2. **Metadata Source**: `analysisMetadata` comes from `useAnalysisMetadata(mergedEvents)`, which extracts metadata from SSE events:
   - For **active analyses**: Metadata extracted from `extraction` stage SSE event
   - For **completed analyses**: Metadata should come from `statusState.progressEvents` (fetched from database)

3. **The Issue**: 
   - `useAnalysisMetadata` only extracts metadata from events where `event.stage === 'extraction' && event.status === 'complete'`
   - For completed analyses loaded via URL, there may be **no SSE events** (page loads after workflow completed)
   - The hook falls back to `statusState.progressEvents` from the database
   - **BUT**: If the database progress events don't have the extraction event with metadata, `analysisMetadata` will be `undefined`

4. **Component Still Renders**: Even with `undefined` metadata, `AnalysisHeader` should render with defaults (`'Content Analysis'` title). However, if `analysisMetadata` is `undefined` AND the component isn't receiving the prop at all, it might not render.

5. **Routing Issue**: The test waits for completion, which means `CompletedAnalysisView` should render. But if `analysisMetadata` is missing, the component might be in a different state.

**Root Cause:**
- **Completed analyses don't have `analysisMetadata` populated** because:
  1. No SSE events exist (workflow already completed)
  2. Database progress events might not include the extraction event with metadata
  3. `useAnalysisMetadata` hook only extracts from extraction stage events
  4. The fallback mechanism (`statusState.progressEvents`) might not contain the extraction event

**Evidence:**
- Test waits for `waitForComplete()` which should show `CompletedAnalysisView`
- `CompletedAnalysisView` includes `AnalysisHeader` with `analysisMetadata` prop
- But `analysisMetadata` is likely `undefined` for completed analyses
- Component should still render with defaults, but something is preventing it

**Why It's Not a Simple Fix:**
- The issue is in the **data flow** for completed analyses
- Need to ensure database progress events include extraction metadata
- OR need to fetch metadata from API separately for completed analyses
- OR need to ensure `useAnalysisMetadata` can extract from database events

## Failure #2: Artifact Has No Code Blocks

**Test**: `artifact.spec.ts:44` - "should display code blocks from markdown"  
**Error**: `codeBlocks.count() === 0` (expected > 0)

### Root Cause Identified

**The Problem:**
The test expects at least 1 code block in the artifact markdown, but finds 0. This is a **content issue**, not a rendering issue.

**Why This Happens:**

1. **Code Block Rendering Works**: 
   - `CodeBlock` component has `data-testid="code-block"` ✅
   - Markdown renderer correctly maps code blocks to `CodeBlock` component ✅
   - The rendering infrastructure is correct

2. **Artifact Content Structure**:
   - Artifacts are generated by the backend as markdown
   - Code blocks in markdown use triple backticks: ` ```language\ncode\n``` `
   - The test uses `getCompletedAnalysis()` which gets a random completed analysis

3. **The Issue**:
   - **Not all artifacts contain code blocks**
   - Artifacts are implementation guides that may or may not include code examples
   - The test assumes ALL artifacts have code blocks, which is **not guaranteed**

4. **Test Data Problem**:
   - `getCompletedAnalysis()` returns a random completed analysis
   - There's no guarantee that analysis's artifact contains code blocks
   - Some artifacts might be conceptual guides without code examples
   - Some artifacts might be text-only tutorials

**Root Cause:**
- **Test assumption is incorrect**: Not all artifacts contain code blocks
- **Test data is random**: `getCompletedAnalysis()` doesn't ensure artifact has code blocks
- **No validation**: Test doesn't check if artifact actually has code blocks before asserting

**Evidence:**
- Code block rendering works (other tests pass)
- Test ID is correct
- The issue is that the **artifact content** doesn't have code blocks
- This is a **test data/expectation issue**, not a code issue

**Why It's Not a Simple Fix:**
- Need to either:
  1. **Use a specific artifact** that's known to have code blocks
  2. **Make test conditional** - skip if no code blocks
  3. **Create test data** with guaranteed code blocks
  4. **Check artifact content** before asserting code blocks exist

## Failure #3: Workflow Stages Not Appearing

**Test**: `full-workflow-13-stages.spec.ts:77` - "should complete full analysis workflow with all 13 stages"  
**Error**: `0 out of 6 core stages` detected via SSE monitoring

### Root Cause Identified

**The Problem:**
The test monitors SSE events for stage names but detects **0 stages**. This means either:
1. SSE events aren't being emitted
2. SSE events have different stage names
3. SSE events aren't being parsed correctly
4. Workflow isn't running

**Why This Happens:**

1. **SSE Event Emission**:
   - Backend uses `emit_streaming_event()` to emit events
   - Events are published to `workflow:{analysis_id}` channel
   - Events have structure: `{ type, stage, status, ... }`

2. **Stage Names**:
   - Backend uses `get_stage_name()` to convert agent types to stage names
   - Stage names come from `AGENT_REGISTRY` in `agent_config.py`
   - Core stages: `extraction`, `embedding`, `supervisor_routing`, `aggregation`, `quality_validation`, `artifact_generation`

3. **The Issue**:
   - **Stage name mismatch**: Test expects `quality_validation` but backend uses `quality_gate`
   - Backend code in `graph_builder.py` shows `quality_gate_node` and `quality_gate_*` variables
   - Test expects `quality_validation` in `CORE_STAGES` array
   - **`quality_validation` is NOT in `AGENT_REGISTRY`** - it's a workflow-level stage
   - **Workflow might not be running** - `SKILLFORGE_E2E_DISABLE_WORKFLOW` might be set

4. **SSE Event Monitoring**:
   - Test monitors `page.on('response')` for SSE endpoint
   - Parses `data: {...}` lines from SSE stream
   - Extracts `stage` field from JSON
   - But if workflow isn't running, no events are emitted

5. **Workflow Execution**:
   - Workflow runs in background task
   - If `SKILLFORGE_E2E_DISABLE_WORKFLOW=true`, workflow is skipped
   - If API keys are missing, workflow might fail silently
   - If workflow fails early, no stages are emitted

**Root Cause:**
- **Stage name mismatch**: Test expects `quality_validation` but backend uses `quality_gate` (confirmed in `graph_builder.py`)
- **Workflow might not be running**: `SKILLFORGE_E2E_DISABLE_WORKFLOW` might be enabled, or workflow failing early
- **SSE events not emitted**: If workflow doesn't run, no events are published
- **Configuration issue**: Missing API keys or workflow disabled for E2E tests

**Evidence:**
- Test monitors SSE endpoint but gets 0 stages
- **Confirmed**: Backend uses `quality_gate` (in `graph_builder.py`), test expects `quality_validation`
- `AGENT_REGISTRY` doesn't include all core stages (only agent stages)
- Workflow stages like `extraction`, `embedding` are workflow-level, not in registry
- `SKILLFORGE_E2E_DISABLE_WORKFLOW` flag exists and can disable workflow execution

**Why It's Not a Simple Fix:**
- Need to verify:
  1. **Workflow is actually running** (check backend logs)
  2. **SSE events are being emitted** (check broadcaster)
  3. **Stage names match** (backend vs test expectations)
  4. **Configuration is correct** (`SKILLFORGE_E2E_DISABLE_WORKFLOW=false`)
  5. **API keys are present** (workflow needs LLM keys)
